## 2. 本讲先记住一句话

```text
repository 只负责找数据。
service 负责判断业务是否成功。
service 失败时抛业务异常。
全局异常处理器负责把业务异常变成 HTTP JSON 响应。
```

完整链路：

```text
HTTP 请求
-> endpoint 接收参数
-> service 执行业务
-> repository 读写数据
-> service 发现业务错误，抛 AppError
-> exception handler 捕获 AppError
-> 返回统一 JSON 错误响应
```

可以先粗略理解为：

```text
service 只说“发生了什么业务错误”。
exception handler 决定“这个错误怎么返回给客户端”。
```

## 4. 先区分几个容易混的词

### 1. 错误

错误是一个比较泛的说法。

例如：

```text
任务不存在
用户不存在
请求字段格式不对
服务器代码写错了
数据库连接失败
```

这些都可以叫错误。

### 2. 异常

异常是 Python 程序里表达错误的一种机制。

例如：

```python
raise ValueError("title cannot be empty")
```

意思是：

```text
程序执行到这里，发现不能继续按正常流程走了，于是抛出一个异常。
```

异常会中断当前函数的正常执行。

比如：

```python
def get_task(task_id: int):
    task = get_existing_task(task_id)
    return build_detail_response("success", task)
```

如果 `get_existing_task(task_id)` 里面抛异常，后面的 `return` 就不会执行。

### 3. HTTP 状态码

HTTP 状态码是返回给客户端看的。

常见状态码：

```text
200 OK：请求成功
201 Created：创建成功
204 No Content：删除成功且没有响应体
400 Bad Request：请求语义不合理
401 Unauthorized：没有登录或认证失败
403 Forbidden：没有权限
404 Not Found：资源不存在
409 Conflict：资源冲突
422 Validation Error：请求格式或字段校验失败
500 Internal Server Error：服务器内部错误
```

重点区别：

```text
异常是 Python 程序内部的概念。
状态码是 HTTP 响应里的概念。
```

FastAPI 的工作之一，就是把 Python 内部发生的异常转换成 HTTP 响应。

### 4. 错误响应体

状态码只能告诉客户端大概发生了什么。

例如：

```text
404
```

它只表示“没找到”。  
但客户端还想知道：

```text
是任务没找到？
是用户没找到？
是项目没找到？
有没有稳定的错误码？
这次请求有没有 request_id？
```

所以真实项目通常会返回错误响应体：

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Task not found",
    "request_id": null
  }
}
```

## 5. 第 05 讲当前错误处理有什么问题

第 05 讲当前项目里，service 层大概这样处理错误：

```python
def get_existing_task(task_id: int) -> dict:
    task = task_repository.get_task_by_id(task_id)
    if task is None:
        raise HTTPException(
            status_code=http_status.HTTP_404_NOT_FOUND,
            detail="Task not found",
        )
    return task
```

这个写法的问题不是“不能用”，而是“后面不够工程化”。

### 问题 1：service 层知道了太多 HTTP 细节

service 本来应该只关心：

```text
有没有这个 task？
owner_id 是否存在？
project_id 是否存在？
是否允许更新？
```

但现在 service 还要知道：

```text
HTTPException 怎么写？
status_code 用多少？
detail 写什么？
```

这让 service 层和 FastAPI 框架绑得更紧。

### 问题 2：错误格式容易不统一

如果每个地方都自己抛 `HTTPException`，很容易出现不同格式。

某个接口返回：

```json
{
  "detail": "Task not found"
}
```

另一个接口可能返回：

```json
{
  "detail": {
    "code": "USER_NOT_FOUND",
    "message": "User not found"
  }
}
```

客户端会很难处理。

统一错误格式的好处是：

```text
所有错误都长得一样。
前端和调用方不用猜字段在哪里。
后面加 request_id、日志追踪、错误码文档都更容易。
```

### 问题 3：以后不好统一加 request_id

后面学中间件时，你会给每个请求生成：

```text
request_id
```

如果错误响应都经过一个全局异常处理器，以后只需要在那里统一加 `request_id`。  
如果每个函数都自己返回错误，就会到处改。

## 7. 什么是业务异常

业务异常就是：

```text
业务规则认为这件事不能继续执行。
```

例如：

```text
任务不存在
用户不存在
项目不存在
任务标题重复
项目已归档，不能再创建任务
普通用户不能删除别人的任务
```

这些不是服务器崩溃，而是业务上可以预期的失败。

比如请求：

```text
GET /api/v1/tasks/999
```

如果任务 999 不存在，服务端不应该崩溃。  
它应该清楚地告诉客户端：

```text
HTTP 状态码：404
业务错误码：TASK_NOT_FOUND
错误信息：Task not found
```

## 8. 定义统一错误响应模型

建议新增：

```text
app/schemas/error.py
```

代码：

```python
from typing import Any

from pydantic import BaseModel


class ErrorDetail(BaseModel):
    code: str
    message: str
    request_id: str | None = None
    details: list[dict[str, Any]] | None = None


class ErrorResponse(BaseModel):
    error: ErrorDetail
```

对应响应：

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Task not found",
    "request_id": null,
    "details": null
  }
}
```

字段解释：

```text
error：统一错误对象
code：机器可读的错误码，适合前端做判断
message：人类可读的错误说明
request_id：请求编号，后面配合中间件和日志使用
details：更详细的错误列表，主要给 422 校验错误使用
```

为什么需要 `code`？

因为 `message` 可能以后会改，甚至可能翻译成中文。  
但 `code` 通常比较稳定。

例如前端可以根据：

```text
TASK_NOT_FOUND
```

判断应该显示：

```text
这个任务不存在或已被删除
```

而不是去解析字符串 `"Task not found"`。

## 9. 定义基础 AppError

建议新增：

```text
app/core/errors.py
```

代码：

```python
from fastapi import status as http_status


class AppError(Exception):
    status_code = http_status.HTTP_400_BAD_REQUEST
    code = "APP_ERROR"
    message = "Application error"

    def __init__(self, message: str | None = None):
        if message is not None:
            self.message = message
```

解释：

```text
AppError 是所有业务异常的父类。
status_code 表示最终应该返回的 HTTP 状态码。
code 表示业务错误码。
message 表示给人看的错误说明。
```

为什么继承 `Exception`？

因为 Python 里自定义异常通常继承 `Exception`，这样你就可以：

```python
raise AppError()
```

也可以让异常处理器捕获它。

## 10. 定义具体业务异常

继续在：

```text
app/core/errors.py
```

里写：

```python
from fastapi import status as http_status


class AppError(Exception):
    status_code = http_status.HTTP_400_BAD_REQUEST
    code = "APP_ERROR"
    message = "Application error"

    def __init__(self, message: str | None = None):
        if message is not None:
            self.message = message


class TaskNotFoundError(AppError):
    status_code = http_status.HTTP_404_NOT_FOUND
    code = "TASK_NOT_FOUND"
    message = "Task not found"


class UserNotFoundError(AppError):
    status_code = http_status.HTTP_404_NOT_FOUND
    code = "USER_NOT_FOUND"
    message = "User not found"


class ProjectNotFoundError(AppError):
    status_code = http_status.HTTP_404_NOT_FOUND
    code = "PROJECT_NOT_FOUND"
    message = "Project not found"


class BusinessRuleError(AppError):
    status_code = http_status.HTTP_400_BAD_REQUEST
    code = "BUSINESS_RULE_ERROR"
    message = "Business rule error"
```

可以这样理解：

```text
AppError 是总类。
TaskNotFoundError 表示任务不存在。
UserNotFoundError 表示用户不存在。
ProjectNotFoundError 表示项目不存在。
BusinessRuleError 表示普通业务规则错误。
```

为什么要分这么细？

因为错误码更清楚。  
如果全都返回 `NOT_FOUND`，客户端不知道到底是任务、用户还是项目不存在。

## 11. 全局异常处理器是什么

全局异常处理器可以理解成：

```text
FastAPI 里专门负责“接住某类异常，并把它变成 HTTP 响应”的函数。
```

比如 service 抛了：

```python

```

异常处理器会把它变成：

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Task not found",
    "request_id": null
  }
}
```

这就是第 06 讲的核心。

## 12. 编写异常处理器

建议新增：

```text
app/core/exception_handlers.py
```

代码：

```python
from fastapi import FastAPI, Request, status as http_status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

from app.core.errors import AppError


def get_request_id(request: Request) -> str | None:
    return getattr(request.state, "request_id", None)


async def app_error_handler(request: Request, exc: AppError) -> JSONResponse:
    return JSONResponse(
        status_code=exc.status_code,
        content={
            "error": {
                "code": exc.code,
                "message": exc.message,
                "request_id": get_request_id(request),
            }
        },
    )


async def validation_error_handler(
    request: Request,
    exc: RequestValidationError,
) -> JSONResponse:
    return JSONResponse(
        status_code=http_status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={
            "error": {
                "code": "VALIDATION_ERROR",
                "message": "Request validation failed",
                "request_id": get_request_id(request),
                "details": exc.errors(),
            }
        },
    )


def register_exception_handlers(app: FastAPI) -> None:
    app.add_exception_handler(AppError, app_error_handler)
    app.add_exception_handler(RequestValidationError, validation_error_handler)
```

解释：

```text
app_error_handler：处理自己定义的业务异常。
validation_error_handler：处理 FastAPI/Pydantic 的 422 校验错误。
register_exception_handlers：把异常处理器注册到 FastAPI app 上。
```

`Request` 是当前请求对象。  
后面学中间件时，我们会把 `request_id` 放到：

```python
request.state.request_id
```

本讲暂时没有中间件，所以 `request_id` 可能是 `null`，这没关系。

`JSONResponse` 用来手动构造 JSON 响应。  
它可以指定：

```text
status_code
content
```

## 15. repository 这一层要不要改

本讲 repository 暂时不用大改。

当前：

```python
def get_task_by_id(task_id: int) -> dict | None:
    return memory_db.tasks.get(task_id)
```

这个写法很好。

因为 repository 只说：

```text
查到了，返回 dict。
没查到，返回 None。
```

它不需要知道：

```text
没查到应该返回 404。
没查到错误码叫 TASK_NOT_FOUND。
没查到响应体怎么组织。
```

这些交给 service 和 exception handler。

基础阶段先这么记：

```text
查数据这件事归 repository。
判断查不到是不是业务错误，归 service。
把业务错误变成 HTTP 响应，归 exception handler。
```

## 16. endpoint 要不要写 try/except

一般不需要。

第 05 讲里的 endpoint 是：

```python
@router.get("/{task_id}", response_model=TaskDetailResponse)
def get_task(task_id: int):
    return task_service.get_task(task_id)
```

第 06 讲仍然保持这样。

不要急着写：

```python
@router.get("/{task_id}", response_model=TaskDetailResponse)
def get_task(task_id: int):
    try:
        return task_service.get_task(task_id)
    except TaskNotFoundError:
        ...
```

如果每个 endpoint 都写一堆 `try/except`，代码又会变乱。  
全局异常处理器就是为了让 endpoint 保持薄一点。

正确思路：

```text
endpoint 调 service。
service 失败就 raise AppError。
全局 handler 统一接住。
```

## 17. 422 和 404 的区别

这一点非常重要。

### 422：请求格式或字段校验没通过

例如：

```text
GET /api/v1/tasks?page=0
```

因为 endpoint 里写了：

```python
page: Annotated[int, Query(ge=1)] = 1
```

`page` 必须大于等于 1。  
所以 `page=0` 还没进入 service，就已经被 FastAPI/Pydantic 拦住了。

这类错误是：

```text
422 Validation Error
```

再比如创建任务时：

```json
{
  "title": "",
  "owner_id": 1,
  "project_id": 1
}
```

因为 `title` 设置了 `min_length=1`，所以也是 422。

### 404：字段格式没问题，但业务资源不存在

例如：

```json
{
  "title": "测试不存在的 owner",
  "owner_id": 999,
  "project_id": 1
}
```

`owner_id=999` 是一个合法整数，也大于等于 1。  
所以 Pydantic 校验会通过。

但是 service 去 repository 查用户时发现：

```text
用户 999 不存在
```

这就是业务资源不存在。

应该返回：

```text
404 USER_NOT_FOUND
```

记住：

```text
字段形状不对 -> 422
字段形状对，但业务对象不存在 -> 404
```

## 22. 常见错误

### 1. 忘记在 main.py 注册异常处理器

你写了：

```text
app/core/exception_handlers.py
```

但如果没有在 `main.py` 里调用：

```python
register_exception_handlers(app)
```

FastAPI 就不知道要使用这些处理器。

### 2. service 里还在导入 HTTPException

第 06 讲之后，`task_service.py` 里尽量不要再出现：

```python
from fastapi import HTTPException
```

因为本讲目标就是把 service 从 HTTPException 里解放出来。

### 3. repository 开始抛 HTTPException

不建议这样：

```python
def get_task_by_id(task_id: int) -> dict:
    task = memory_db.tasks.get(task_id)
    if task is None:
        raise HTTPException(...)
    return task
```

repository 先保持简单：

```python
def get_task_by_id(task_id: int) -> dict | None:
    return memory_db.tasks.get(task_id)
```

### 4. endpoint 到处写 try/except

不要每个 endpoint 都手动抓：

```python
try:
    return task_service.get_task(task_id)
except TaskNotFoundError:
    ...
```

全局异常处理器就是为了避免这种重复。

### 5. 把业务错误返回成 200

不要让任务不存在返回：

```text
200 OK
```

任务不存在应该是：

```text
404 Not Found
```

错误响应体和 HTTP 状态码要配合起来。

### 6. 混淆 422 和 404

记住：

```text
owner_id = "abc" -> 422，因为类型不对
owner_id = 999 -> 404，因为类型对，但用户不存在
```

### 7. 以为 500 是正常业务错误

500 通常表示：

```text
服务器内部没处理好的异常
```

业务上能预期的错误，尽量不要让它变成 500。

## 23. 本讲和第 05 讲的关系

第 05 讲解决的是：

```text
代码放在哪里。
```

第 06 讲解决的是：

```text
错误在哪里产生，在哪里统一返回。
```

第 05 讲的正常调用链路：

```text
endpoint -> service -> repository
```

第 06 讲补上错误链路：

```text
service raise AppError
-> FastAPI exception handler
-> JSONResponse
-> client
```

合起来就是：

```text
正常流程：
endpoint -> service -> repository -> service -> endpoint -> response_model

错误流程：
endpoint -> service -> AppError -> exception_handler -> JSONResponse
```

## 25. 今日重点理解

今天最重要的是这几句话：

```text
1. HTTPException 是 FastAPI 的 HTTP 错误工具。
2. 入门阶段可以直接用 HTTPException，但分层后 service 更适合抛业务异常。
3. AppError 是所有业务异常的父类。
4. TaskNotFoundError、UserNotFoundError、ProjectNotFoundError 是具体业务异常。
5. 全局异常处理器负责把业务异常转换成统一 JSON 响应。
6. repository 只负责数据访问，查不到可以返回 None。
7. endpoint 不需要到处写 try/except。
8. 422 是请求校验失败，404 是资源不存在。
9. 错误响应要统一，方便前端和调用方处理。
10. 这一步是在为 Depends、中间件、request_id、日志打基础。
```
