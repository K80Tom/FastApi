### 第 02 讲：请求体、HTTP 方法与内存版任务 CRUD

完成状态：已整理笔记，已在 `01_练习/02.py` 中写出内存版任务 CRUD 示例代码，下一步进行接口联调测试。

已经学习的概念：

- 客户端向服务端发送 HTTP 请求。
- 服务端接收请求、执行 Python 函数、返回 HTTP 响应。
- 请求体用于承载客户端提交给服务端的复杂数据。
- 响应体用于承载服务端返回给客户端的数据。
- `Body(...)` 表示从请求体中读取必填数据。
- `return dict/list` 会被 FastAPI 转成 JSON 响应体。
- `POST /tasks` 用于创建任务。
- `PUT /tasks/{task_id}` 用于整体替换任务。
- `PATCH /tasks/{task_id}` 用于局部更新任务。
- `DELETE /tasks/{task_id}` 用于删除任务。
- 内存字典 `tasks = {}` 可以临时保存任务数据。
- `next_task_id` 可以用于生成任务 id。
- `HTTPException` 可以主动返回业务错误。
- 任务不存在时应该返回 `404 Not Found`。
- 删除成功且不返回内容时可以使用 `204 No Content`。
- 请求数据不符合业务规则时可以返回 `400 Bad Request`。
- 路径参数类型不匹配时 FastAPI 可能返回 `422 Validation Error`。

已经写出的接口：

```text
GET /health
GET /tasks
GET /tasks/{task_id}
POST /tasks
PUT /tasks/{task_id}
PATCH /tasks/{task_id}
DELETE /tasks/{task_id}
```

今日核心理解：

```text
客户端请求体 JSON
-> FastAPI 读取 Body
-> Python dict
-> 手动校验字段
-> 写入或修改内存字典
-> return 返回 Python dict
-> FastAPI 转成 JSON 响应体
-> 客户端收到状态码和响应体
```

本讲暂时先手动校验字段，而不是一开始就上 Pydantic。原因是：

```text
先把请求体、响应体、HTTP 方法、状态码、CRUD 数据流想清楚。
等这些基础稳定后，再用 Pydantic 把手动校验升级成模型校验。
```

### 第 03 讲：Pydantic 请求模型与响应模型

完成状态：已整理笔记，已在 `01_练习/03.py` 中写出 Pydantic 版任务 CRUD 示例代码，下一步进行 Swagger UI 测试。

已经学习的概念：

- `BaseModel` 用来定义请求体和响应体的数据结构。
- `TaskCreate` 负责创建任务时的请求体校验。
- `TaskUpdate` 负责 PATCH 局部更新时的请求体校验。
- `TaskRead` 负责任务详情响应体。
- `TaskListItem` 负责任务列表里的单个任务摘要。
- `TaskListResponse` 负责分页列表响应结构。
- `Field(...)` 表示必填字段。
- `Field(default=...)` 表示字段默认值。
- `min_length`、`max_length` 可以限制字符串长度。
- `Enum` 可以限制 `status`、`priority` 只能取固定值。
- `ConfigDict(extra="forbid")` 可以拒绝客户端提交多余字段。
- `ConfigDict(str_strip_whitespace=True)` 可以自动去掉字符串前后空格。
- `model_validator(mode="after")` 可以做模型级校验。
- `model_dump()` 可以把 Pydantic 模型转换成普通 Python 字典。
- `exclude_unset=True` 适合 PATCH，只取客户端真正传入的字段。
- `response_model` 可以约束接口返回结构，并过滤内部字段。
- Pydantic 校验失败时，FastAPI 会自动返回 `422 Validation Error`。

已经写出的接口：

```text
GET /health
GET /tasks
GET /tasks/{task_id}
POST /tasks
PUT /tasks/{task_id}
PATCH /tasks/{task_id}
DELETE /tasks/{task_id}
```

今日核心理解：

```text
客户端 JSON 请求体
-> FastAPI 交给 Pydantic 模型
-> Pydantic 自动校验字段类型、长度、枚举值和多余字段
-> 接口函数拿到 TaskCreate / TaskUpdate 对象
-> 业务逻辑写入或修改内存字典
-> response_model 控制最终返回给客户端的数据结构
```

第 03 讲和第 02 讲的关系：

```text
第 02 讲：先用 dict + 手动校验理解 CRUD 数据流
第 03 讲：再用 Pydantic 把手动校验升级成模型校验
```

### 第 04 讲：Pydantic 模型拆分、嵌套模型与规范响应结构

完成状态：已整理笔记，已在 `01_练习/04.py` 中写出更规范的 Pydantic 版 TaskHub API，下一步进行 Swagger UI 测试。

已经学习的概念：

- Pydantic 模型可以继续拆分，不需要一个模型用到底。
- `UserSummary` 表示用户摘要响应模型。
- `ProjectSummary` 表示项目摘要响应模型。
- `TaskTagInput` 表示请求里的标签模型。
- `TaskTagRead` 表示响应里的标签模型。
- `TaskBase` 可以承载创建和整体替换共用字段。
- `TaskCreate(TaskBase)` 表示 `TaskCreate` 继承 `TaskBase` 的字段。
- 嵌套模型可以表达对象里面还有对象，例如 `owner: UserSummary`。
- `list[TaskTagInput]` 表示列表里的每个元素都要符合 `TaskTagInput`。
- `Field(default_factory=list)` 适合给列表字段设置默认空列表。
- 请求体里常提交 `owner_id` / `project_id`，响应体里常返回 `owner` / `project` 对象。
- `PageMeta` 用来表达分页信息。
- `TaskListResponse` 用 `code`、`message`、`data`、`meta` 组织列表响应。
- `TaskDetailResponse` 用 `code`、`message`、`data` 组织详情响应。
- `response_model` 可以继续过滤内部字段，例如 `owner_id`、`project_id`、`internal_note`。
- 422 表示请求格式或字段校验失败，404 表示引用的资源不存在。

已经写出的接口：

```text
GET /health
GET /users
GET /projects
GET /tasks
GET /tasks/{task_id}
POST /tasks
PUT /tasks/{task_id}
PATCH /tasks/{task_id}
DELETE /tasks/{task_id}
```

今日核心理解：

```text
客户端提交简单 id
-> Pydantic 校验请求体
-> 服务端检查 id 对应的用户和项目是否存在
-> 内部保存 owner_id / project_id
-> 响应时补充 owner / project 嵌套对象
-> response_model 控制最终对外结构
```

第 04 讲和第 03 讲的关系：

```text
第 03 讲：用 Pydantic 替代手动校验
第 04 讲：用 Pydantic 表达更真实的嵌套结构和统一响应
```

### 第 05 讲：APIRouter、项目结构与分层入门

完成状态：已整理笔记，已在 `01_练习/05_taskhub_api` 中生成多文件 TaskHub API 项目，下一步进行 Swagger UI 测试。

已经学习的概念：

- 单文件适合入门，多文件结构适合真实项目。
- `APIRouter` 可以把接口按业务模块拆开。
- `/api/v1` 是 API 版本前缀。
- `main.py` 负责创建 FastAPI app 和注册 router。
- `app/api/v1/router.py` 负责统一收集各模块 router。
- `endpoints` 目录负责 HTTP 接口函数。
- `schemas` 目录负责 Pydantic 请求模型和响应模型。
- `services` 目录负责业务逻辑。
- `repositories` 目录负责数据访问。
- `memory_db.py` 暂时用内存字典模拟数据库。
- endpoint 应该薄一点，把业务交给 service。
- service 可以调用 repository 获取或保存数据。
- repository 暂时返回 dict 或 None，不直接处理 HTTP 响应。
- 启动多文件项目时要使用 `uvicorn app.main:app --reload`。
- 本讲接口统一变成 `/api/v1/...`。

已经写出的接口：

```text
GET /api/v1/health
GET /api/v1/users
GET /api/v1/projects
GET /api/v1/tasks
GET /api/v1/tasks/{task_id}
POST /api/v1/tasks
PUT /api/v1/tasks/{task_id}
PATCH /api/v1/tasks/{task_id}
DELETE /api/v1/tasks/{task_id}
```

今日核心理解：

```text
HTTP 请求
-> endpoint 接收参数
-> service 执行业务规则
-> repository 读写数据
-> service 组装响应
-> endpoint 交给 response_model 输出
```

第 05 讲和第 04 讲的关系：

```text
第 04 讲：先把 Pydantic 数据结构设计清楚
第 05 讲：再把这些代码放到真实项目目录里
```
