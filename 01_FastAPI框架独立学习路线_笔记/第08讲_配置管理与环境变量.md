## 4. 什么是 .env 文件

`.env` 文件是一个纯文本文件，用来存放环境变量。

格式很简单：

```text
APP_NAME=TaskHub API
APP_VERSION=0.1.0
DEBUG=true
DATABASE_URL=postgresql://user:pass@localhost:5432/taskhub
SECRET_KEY=my-secret-key-123
```

每一行是 `KEY=VALUE`。

它的作用是：

```text
把配置从代码中分离出来。
不同环境用不同的 .env 文件。
```

比如：

```text
开发环境 .env：
DEBUG=true
DATABASE_URL=postgresql://localhost/taskhub_dev

生产环境 .env：
DEBUG=false
DATABASE_URL=postgresql://prod-server/taskhub
```

代码不用改，只换 .env 文件。

## 5. 什么是 Pydantic Settings

Pydantic Settings 是 Pydantic 的一个扩展库，专门用来做配置管理。

它的核心类是 `BaseSettings`，和你之前学的 `BaseModel` 类似：

```text
BaseModel：定义请求体和响应体的数据结构。
BaseSettings：定义应用配置的数据结构。
```

区别在于：

```text
BaseModel 的值来自 JSON 请求体。
BaseSettings 的值来自环境变量或 .env 文件。
```

安装：

```powershell
pip install pydantic-settings
```

基本用法：

```python
from pydantic_settings import BaseSettings


class Settings(BaseSettings):
    app_name: str = "TaskHub API"
    debug: bool = False
```

当你创建 `Settings()` 时：

```text
1. 先看有没有环境变量 APP_NAME、DEBUG
2. 如果有，用环境变量的值
3. 如果没有，用代码里定义的默认值
```

注意命名规则：

```text
Python 字段名：app_name（小写下划线）
环境变量名：APP_NAME（大写下划线）
```

Pydantic Settings 自动做大小写转换。

## 6. 配置类完整设计

本讲的配置类放在：

```text
app/core/config.py
```

完整代码：

```python
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    """应用配置。

    值的加载优先级（从高到低）：
    1. 系统环境变量
    2. .env 文件
    3. 代码里的默认值
    """

    # 应用基础信息
    app_name: str = "TaskHub API"
    app_version: str = "0.1.0"
    debug: bool = False

    # API 配置
    api_prefix: str = "/api/v1"

    # 后续会用到的配置（先留默认值）
    database_url: str = "sqlite:///./taskhub.db"
    secret_key: str = "change-me-in-production"
    access_token_expire_minutes: int = 30

    # CORS
    cors_origins: list[str] = ["http://localhost:3000"]

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        case_sensitive=False,
    )
```

逐行解释：

```text
class Settings(BaseSettings):
    继承 BaseSettings，表示这是一个配置类。

app_name: str = "TaskHub API"
    字段名 app_name，类型 str，默认值 "TaskHub API"。
    对应环境变量 APP_NAME。

debug: bool = False
    布尔类型。环境变量里写 true/false/1/0 都能识别。

cors_origins: list[str] = [...]
    列表类型。环境变量里可以写 JSON 格式：
    CORS_ORIGINS=["http://localhost:3000","http://localhost:8080"]

model_config = SettingsConfigDict(...)
    配置 Settings 类本身的行为。
    env_file=".env" 表示从 .env 文件加载。
    case_sensitive=False 表示环境变量名不区分大小写。
```

## 7. SettingsConfigDict 是什么

`SettingsConfigDict` 用来配置 Settings 类本身的加载行为。

常用选项：

```text
env_file = ".env"
    指定 .env 文件路径。

env_file_encoding = "utf-8"
    .env 文件编码。

case_sensitive = False
    环境变量名是否区分大小写。
    False 表示 APP_NAME 和 app_name 都能匹配。

env_prefix = "TASKHUB_"
    给所有环境变量加前缀。
    设置后，app_name 对应 TASKHUB_APP_NAME。
```

本讲暂时不加 `env_prefix`，保持简单。

后面如果你的服务器上跑了多个项目，用前缀可以避免环境变量冲突：

```text
TASKHUB_DATABASE_URL=...
TASKHUB_SECRET_KEY=...
```

## 9. 为什么 .env 不应该提交到 Git

`.env` 文件通常包含敏感信息：

```text
SECRET_KEY=my-real-secret
DATABASE_URL=postgresql://user:password@host/db
```

如果推送到 Git：

```text
任何能看到代码仓库的人都能看到你的密钥。
```

正确做法：

```text
1. .env 放在 .gitignore 里，不提交。
2. 提供一个 .env.example 文件，写上所有配置项但不写真实值。
3. 其他开发者 clone 项目后，复制 .env.example 为 .env，填入自己的值。
```

`.env.example` 示例：

```text
APP_NAME=TaskHub API
APP_VERSION=0.1.0
DEBUG=true
API_PREFIX=/api/v1
DATABASE_URL=sqlite:///./taskhub.db
SECRET_KEY=change-me
ACCESS_TOKEN_EXPIRE_MINUTES=30
CORS_ORIGINS=["http://localhost:3000"]
```

`.gitignore` 加一行：

```text
.env
```

## 10. 用 lru_cache 缓存配置对象

每次调用 `Settings()` 都会重新读取 .env 文件和环境变量。

如果每个请求都创建一个新的 Settings 对象，会有不必要的 I/O 开销。

解决方案：用 `lru_cache` 缓存。

```python
from functools import lru_cache

from app.core.config import Settings


@lru_cache
def get_settings() -> Settings:
    """缓存配置对象，整个应用生命周期只创建一次。"""
    return Settings()
```

`@lru_cache` 的作用：

```text
第一次调用 get_settings() -> 创建 Settings 对象，缓存起来。
后续调用 get_settings() -> 直接返回缓存的对象，不再重新创建。
```

这样整个应用只会读一次 .env 文件。

## 11. 把 get_settings 加入依赖系统

第 07 讲你已经学了 Depends。现在把配置也接入依赖系统。

修改 `app/core/dependencies.py`：

```python
"""公共依赖函数。"""

from functools import lru_cache
from typing import Annotated

from fastapi import Depends

from app.core.config import Settings
from app.services import task_service as _task_service_module


@lru_cache
def get_settings() -> Settings:
    """返回缓存的配置对象。"""
    return Settings()


def get_task_service():
    """返回 task_service 模块，供 endpoint 通过 Depends 注入。"""
    return _task_service_module


# 类型别名，方便 endpoint 使用
SettingsDep = Annotated[Settings, Depends(get_settings)]
```

在 endpoint 里使用：

```python
from app.core.dependencies import SettingsDep


@router.get("/health")
def health_check(settings: SettingsDep):
    return {
        "status": "ok",
        "app_name": settings.app_name,
        "version": settings.app_version,
        "debug": settings.debug,
    }
```

这样 health 接口就能返回应用配置信息了。

## 13. 配置值的加载优先级

Pydantic Settings 加载配置时有优先级：

```text
优先级从高到低：

1. 系统环境变量（已经设置的）
2. .env 文件里的值
3. 代码里的默认值
```

举例：

```text
代码里写了：app_name: str = "TaskHub API"
.env 里写了：APP_NAME=My TaskHub
系统环境变量：APP_NAME=Production TaskHub

最终 settings.app_name = "Production TaskHub"
```

这个优先级很重要：

```text
开发时：用 .env 文件配置。
Docker 部署时：用环境变量覆盖，不需要修改 .env。
```

Docker Compose 示例（后面第 8 周会用到）：

```yaml
services:
  api:
    environment:
      - APP_NAME=TaskHub Production
      - DEBUG=false
      - DATABASE_URL=postgresql://db:5432/taskhub
```

## 14. 布尔值和列表的解析

### 布尔值

Pydantic Settings 对布尔值的解析很灵活：

```text
以下值都会被解析为 True：
true, True, TRUE, 1, yes, on

以下值都会被解析为 False：
false, False, FALSE, 0, no, off
```

所以 .env 里可以写：

```text
DEBUG=true
DEBUG=1
DEBUG=yes
```

都能正确解析为 `settings.debug = True`。

### 列表

列表类型需要在 .env 里写 JSON 格式：

```text
CORS_ORIGINS=["http://localhost:3000","http://localhost:8080"]
```

Pydantic Settings 会自动把 JSON 字符串解析成 Python 列表。

如果写错了格式：

```text
CORS_ORIGINS=http://localhost:3000,http://localhost:8080
```

这样不是有效的 JSON，会报验证错误。

## 15. 配置分组的思路

当配置项越来越多时，可以按功能分组。

现阶段不需要拆分，但了解一下思路：

```text
方式一：所有配置放一个类（本讲的做法，适合小项目）

方式二：按功能拆分成多个类（适合大项目）
```

方式二示例（后面项目变大时可以参考）：

```python
class DatabaseSettings(BaseSettings):
    url: str = "sqlite:///./taskhub.db"
    echo: bool = False

    model_config = SettingsConfigDict(env_prefix="DB_")


class AuthSettings(BaseSettings):
    secret_key: str = "change-me"
    token_expire_minutes: int = 30

    model_config = SettingsConfigDict(env_prefix="AUTH_")


class Settings(BaseSettings):
    app_name: str = "TaskHub API"
    debug: bool = False

    db: DatabaseSettings = DatabaseSettings()
    auth: AuthSettings = AuthSettings()
```

对应的环境变量：

```text
DB_URL=postgresql://...
DB_ECHO=true
AUTH_SECRET_KEY=my-secret
AUTH_TOKEN_EXPIRE_MINUTES=60
```

本讲先不这样拆，用单个 Settings 类就够了。

## 20. 如果缺少必填配置会怎样

如果你在 Settings 里定义一个没有默认值的字段：

```python
class Settings(BaseSettings):
    app_name: str = "TaskHub API"
    required_field: str  # 没有默认值，必须提供
```

启动时如果 .env 和环境变量里都没有 `REQUIRED_FIELD`，会报错：

```text
pydantic_settings.errors.SettingsError: 
  required_field
    Field required [type=missing, ...]
```

这就是 Pydantic Settings 的验证能力：

```text
类型错误 -> 启动时就报错，不会等到运行时才发现。
缺少必填 -> 启动时就报错，不会用 None 带着问题跑。
```

本讲的所有字段都有默认值，所以即使没有 .env 文件也能启动。

但后面生产环境可能会把 `secret_key` 改成没有默认值：

```python
secret_key: str  # 生产环境必须显式配置，不能用默认值
```

这样忘记配置密钥时，应用直接启动失败，而不是用不安全的默认值运行。

## 21. lru_cache 和测试

`@lru_cache` 会缓存 Settings 对象。

测试时你可能需要用不同的配置，这时候用 `dependency_overrides`：

```python
from fastapi.testclient import TestClient

from app.main import app
from app.core.config import Settings
from app.core.dependencies import get_settings


def get_test_settings():
    """测试用的配置。"""
    return Settings(
        app_name="Test TaskHub",
        debug=True,
        secret_key="test-secret",
    )


# 替换依赖
app.dependency_overrides[get_settings] = get_test_settings

client = TestClient(app)
response = client.get("/api/v1/health")
assert response.json()["app_name"] == "Test TaskHub"

# 还原
app.dependency_overrides.clear()
```

这就是第 07 讲学的 dependency_overrides 的实际用途之一：

```text
测试时注入不同的配置，不需要真的改 .env 文件。
```

## 23. 常见错误

### 1. 没有安装 pydantic-settings

如果启动时报：

```text
ModuleNotFoundError: No module named 'pydantic_settings'
```

说明没有安装。执行：

```powershell
pip install pydantic-settings
```

注意：Pydantic v2 把 Settings 拆成了独立包。

```text
Pydantic v1：from pydantic import BaseSettings（内置）
Pydantic v2：from pydantic_settings import BaseSettings（独立包）
```

本讲用的是 Pydantic v2 的写法。

### 2. .env 文件位置不对

Pydantic Settings 默认从当前工作目录找 `.env`。

如果你在错误的目录启动：

```text
错误：在 01_FastAPI框架独立学习路线_笔记 目录下启动
正确：在 05_taskhub_api 目录下启动
```

确保 `.env` 文件和启动命令在同一个目录：

```powershell
cd 05_taskhub_api
uvicorn app.main:app --reload
```

### 3. .env 格式错误

常见格式错误：

```text
错误：APP_NAME = TaskHub API    （等号两边有空格，某些解析器有问题）
正确：APP_NAME=TaskHub API

错误：CORS_ORIGINS=localhost:3000,localhost:8080    （不是 JSON）
正确：CORS_ORIGINS=["http://localhost:3000","http://localhost:8080"]

错误：DEBUG=True    （不影响，但建议统一小写）
推荐：DEBUG=true
```

### 4. 修改 .env 后没有重启

因为用了 `@lru_cache`，配置对象只创建一次。

修改 .env 后必须重启 uvicorn 才能生效。

```text
uvicorn --reload 只监听 .py 文件变化。
.env 文件变化不会触发自动重启。
```

### 5. 混淆 BaseModel 和 BaseSettings

```text
BaseModel：用于定义请求体和响应体。值来自 JSON。
BaseSettings：用于定义应用配置。值来自环境变量。
```

不要用 BaseModel 定义配置，也不要用 BaseSettings 定义请求体。

### 6. 在 endpoint 里直接 import Settings 并实例化

错误写法：

```python
from app.core.config import Settings

@router.get("/health")
def health_check():
    settings = Settings()  # 每次请求都创建新对象，读 .env
    return {"app_name": settings.app_name}
```

正确写法：

```python
from app.core.dependencies import SettingsDep

@router.get("/health")
def health_check(settings: SettingsDep):
    return {"app_name": settings.app_name}
```

通过 Depends 注入的好处：

```text
1. 有 lru_cache 缓存，不会重复创建。
2. 测试时可以用 dependency_overrides 替换。
3. 统一管理，其他开发者知道配置从哪来。
```

## 24. 语法重点解释

### 1. `@lru_cache` 是什么

```python
from functools import lru_cache

@lru_cache
def get_settings() -> Settings:
    return Settings()
```

`lru_cache` 是 Python 标准库的装饰器。

LRU = Least Recently Used（最近最少使用）。

对于无参函数：

```text
第一次调用：执行函数体，缓存返回值。
后续调用：直接返回缓存值，不执行函数体。
```

相当于：

```python
_cached_settings = None

def get_settings():
    global _cached_settings
    if _cached_settings is None:
        _cached_settings = Settings()
    return _cached_settings
```

但 `@lru_cache` 更简洁。

### 2. `SettingsConfigDict` 和 Pydantic v2 的 `model_config`

Pydantic v2 用 `model_config` 替代了 v1 的内部 `class Config`。

```text
Pydantic v1（旧写法）：
class Settings(BaseSettings):
    class Config:
        env_file = ".env"

Pydantic v2（新写法）：
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env")
```

本讲用的是 v2 写法。如果你看到网上有 `class Config` 的写法，那是旧版本。

### 3. `list[str]` 类型提示

```python
cors_origins: list[str] = ["http://localhost:3000"]
```

这是 Python 3.9+ 的写法。

等价于旧写法：

```python
from typing import List
cors_origins: List[str] = ["http://localhost:3000"]
```

本项目用 Python 3.10+，可以直接用 `list[str]`。

### 4. 为什么 Depends 参数需要类型别名

```python
SettingsDep = Annotated[Settings, Depends(get_settings)]
```

好处：

```text
1. 多个 endpoint 共用时不需要重复写 Depends(get_settings)。
2. 类型标注清晰，IDE 能给出 Settings 的属性提示。
3. 改依赖函数时只改一处。
```

对比：

```python
# 不用别名：每个 endpoint 都要写完整
def health_check(settings: Annotated[Settings, Depends(get_settings)]):
    ...

def list_tasks(settings: Annotated[Settings, Depends(get_settings)]):
    ...

# 用别名：简洁统一
def health_check(settings: SettingsDep):
    ...

def list_tasks(settings: SettingsDep):
    ...
```

## 30. 今日重点理解

今天最重要的是这几句话：

```text
1. 配置不写死在代码里，从 .env 或环境变量加载。

4. 优先级：系统环境变量 > .env 文件 > 代码默认值。
5. @lru_cache 保证配置对象只创建一次。
6. 通过 Depends(get_settings) 注入配置，和注入 service 是同一个模式。
7. .env 不提交 Git，.env.example 提交 Git。
8. Docker 部署时用环境变量覆盖配置。
9. 测试时用 dependency_overrides 注入测试配置。
10. 必填配置缺失时，应用启动就会报错，不会带着问题跑。
```
