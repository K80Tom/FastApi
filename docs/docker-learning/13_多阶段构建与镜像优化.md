# 13 多阶段构建与镜像优化

## 1. 这一节要解决什么问题

帮你把臃肿的镜像变小。镜像体积直接影响拉取速度、存储成本和安全风险。通过多阶段构建和几个优化技巧，把镜像体积减少 50%~90%。

## 2. 基础概念解释

### 多阶段构建（Multi-stage Build）

通俗解释：构建一个应用分两步：第一步用"建筑工地"（有编译工具、构建依赖）把应用编译好；第二步把编译产物搬进"精装交付房"（干净的小镜像），建筑工地的脏乱差都不要了。

技术解释：一个 Dockerfile 里可以有多个 FROM 指令，每个 FROM 开始一个新的构建阶段。后面的阶段可以用 `COPY --from=阶段名` 从前面的阶段复制文件，最终镜像只包含最后一个阶段的内容。

## 3. 关键知识点

### 3.1 为什么镜像会很大

```bash
# 查看镜像大小
docker images

# 一个未优化的 Python 镜像可能有 1GB+
# 原因：
# - 基础镜像选了 python:3.11（包含完整 Debian + 开发工具）
# - 安装了编译依赖（gcc、python-dev 等）
# - 安装后没有清理 apt 缓存
# - 把测试代码、文档、.git 目录也复制进去了
```

### 3.2 基础镜像的选择

```dockerfile
# 从大到小：
python:3.11              # ~1GB（完整 Debian + 开发工具）
python:3.11-slim         # ~130MB（精简 Debian，去掉了大量非必要包）
python:3.11-alpine       # ~55MB（基于 Alpine Linux，极小）

# 注意：alpine 体积最小，但有兼容性问题
# - 用 musl libc 而不是 glibc，一些二进制包不兼容
# - pip 安装某些包需要编译，速度慢
# - 推荐：优先试 slim，有问题再考虑 alpine
```

### 3.3 单阶段优化技巧

```dockerfile
FROM python:3.11-slim

WORKDIR /app

# 技巧一：pip 安装时不要缓存（减小体积）
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 技巧二：apt 安装完立刻清理缓存（在同一个 RUN 里！）
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
       libpq-dev \
    && apt-get clean \
    && rm -rf /var/lib/apt/lists/*

# 技巧三：.dockerignore 排除无用文件
# （见 .dockerignore 部分）

COPY . .

CMD ["python", "app.py"]
```

`.dockerignore`（减少构建上下文大小）：
```
.git
.gitignore
.env
.env.*
__pycache__
*.pyc
*.pyo
.pytest_cache
tests/
docs/
*.md
node_modules
.vscode
.idea
```

### 3.4 多阶段构建：Python 示例

```dockerfile
# ===== 阶段一：构建阶段（有编译工具）=====
FROM python:3.11 AS builder

WORKDIR /build

# 安装编译依赖（只在 builder 阶段需要）
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc libpq-dev \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .

# 把依赖安装到指定目录
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt


# ===== 阶段二：运行阶段（精简镜像）=====
FROM python:3.11-slim AS runtime

WORKDIR /app

# 只复制安装好的依赖（不要编译工具）
COPY --from=builder /install /usr/local

# 复制应用代码
COPY . .

# 非 root 用户
RUN useradd -m -u 1000 appuser
USER appuser

CMD ["python", "app.py"]
```

效果对比（示例）：
```
未优化（FROM python:3.11 + 编译工具）：~1.2 GB
多阶段构建（最终 FROM python:3.11-slim）：~180 MB
```

### 3.5 多阶段构建：Go 应用（极致精简）

Go 可以编译出完全静态的二进制，最终镜像可以只有几 MB：

```dockerfile
# ===== 阶段一：编译 =====
FROM golang:1.22-alpine AS builder

WORKDIR /src

# 先复制 go.mod 和 go.sum，利用缓存
COPY go.mod go.sum ./
RUN go mod download

# 复制源码并编译
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server .


# ===== 阶段二：运行（几乎空的镜像）=====
FROM scratch AS runtime    # scratch 是空镜像！

# 只复制编译好的二进制
COPY --from=builder /app/server /server

# 如果需要 HTTPS，还需要复制 CA 证书
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/

EXPOSE 8080
ENTRYPOINT ["/server"]
```

效果：
```
FROM golang:1.22-alpine：~300MB
FROM scratch + 二进制：~10MB
```

### 3.6 多阶段构建：Node.js 前端

```dockerfile
# ===== 阶段一：构建前端 =====
FROM node:20-alpine AS builder

WORKDIR /build

COPY package*.json ./
RUN npm ci --only=production

COPY . .
RUN npm run build


# ===== 阶段二：用 nginx 提供静态文件 =====
FROM nginx:1.25-alpine AS runtime

# 只复制构建产物
COPY --from=builder /build/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80
```

效果：
```
node:20-alpine + 源码 + node_modules：~500MB
nginx:alpine + 静态文件：~25MB
```

### 3.7 构建特定阶段

```bash
# 只构建到某个阶段（调试时有用）
docker build --target builder -t myapp:builder .

# 正常构建（默认构建最后一个阶段）
docker build -t myapp:latest .
```

### 3.8 优化效果总结

| 技巧 | 典型收益 |
| --- | --- |
| 换 slim 基础镜像 | -50% ~ -80% |
| 换 alpine 基础镜像 | -80% ~ -95%（有兼容性风险） |
| pip/npm --no-cache | -10% ~ -30% |
| apt 清理缓存 | -5% ~ -20% |
| 多阶段构建（去掉编译工具） | -40% ~ -80% |
| .dockerignore | 减小构建上下文，加快构建速度 |
| 使用 scratch 基础镜像（Go） | 最终镜像只有二进制，极致精简 |

## 4. 和前后知识的关系

多阶段构建是 `07_Dockerfile` 的进阶，`12_镜像仓库` 里推送的镜像如果很小，可以大幅减少拉取时间。

## 5. 实战任务

1. 找一个你有的项目（或者用示例），先用普通 Dockerfile 构建，记录镜像大小。
2. 改为多阶段构建，对比优化前后的大小。
3. 运行 `docker history 镜像名`，找出哪一层最大，想想能不能优化。

## 6. 常见误区

1. 误区：在 RUN 里用单独的 `&&` 来 `rm -rf` 删除文件能减小镜像。  
   解释：只有在**同一个 RUN 指令**里安装并清理才有效。如果第一个 RUN 装了，第二个 RUN 删，第一层的文件还在，镜像不会变小。

2. 误区：alpine 一定比 slim 好。  
   解释：alpine 最小，但基于 musl libc，某些 Python C 扩展包（numpy、pandas、psycopg2 等）需要重新编译，而且有兼容性问题。优先用 slim，只有明确需要极致精简时才用 alpine。

## 7. 本节总结

镜像优化三板斧：选小基础镜像（slim > alpine 视情况）、清理构建缓存（在同一 RUN 里）、多阶段构建（把编译工具留在 builder 阶段，运行阶段只放必要文件）。Go 应用可以用 scratch 基础镜像实现极致精简。`.dockerignore` 是容易被忽视的优化点，能减小构建上下文，加快构建。
