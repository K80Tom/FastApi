# 06 镜像详解与镜像分层

## 1. 这一节要解决什么问题

帮你深入理解 Docker 镜像的分层结构（Union File System）、镜像是怎么被构建和存储的，以及这些原理如何影响你写 Dockerfile 时的性能和效率。

## 2. 基础概念解释

### 联合文件系统（Union File System / UnionFS）

通俗解释：UnionFS 是一种"叠加"文件系统，把多个只读层叠在一起，看起来像一个单一的文件系统。最上面加一个可写层，你对文件的修改都写在最上面那层。

技术解释：Docker 使用 OverlayFS（Linux 内核原生支持）实现分层。每个镜像层是一个只读的文件系统快照，多个层通过 overlay 合并呈现为一个完整的视图。容器启动时在最上面加一个可写层（container layer）。

例子：想象叠了几张透明纸，每张纸上画了一些内容，叠在一起看是完整的画。如果你想改某个地方，在最上面加一张新纸写上改动。原来的纸（只读层）不变。

### 镜像层（Layer）

通俗解释：Dockerfile 里的每一条指令（RUN/COPY/ADD 等）都会产生一个新的"层"，层叠加起来就是完整的镜像。

技术解释：每个层存储了相对于上一层的文件系统变化（增删改）。层有唯一的 SHA256 哈希值作为 ID，相同 ID 的层在磁盘上只存一份，可以被多个镜像共享。

## 3. 为什么要学这个

理解镜像分层是写出高效 Dockerfile 的基础。知道"构建缓存是什么、为什么缓存会失效、如何利用缓存加速构建"，能让镜像构建从几分钟变成几秒钟。

最下面的层（ADD file 那层）是基础 OS 层（Debian），往上是 nginx 安装层，再往上是配置层。

### 4.2 分层的存储与共享

```bash
# 查看 Docker 的存储驱动和层存储位置
docker info | grep "Storage Driver"
# 通常是 overlay2

# 查看磁盘使用（体现了层共享的效果）
docker system df -v
```

共享的效果示意：
```
镜像 A：ubuntu:22.04（100MB）
镜像 B：python:3.11（基于 ubuntu:22.04 + Python，额外 60MB）
镜像 C：你的应用（基于 python:3.11 + 依赖，额外 20MB）

磁盘实际占用：100 + 60 + 20 = 180MB
表面上三个镜像大小之和：100 + 160 + 180 = 440MB
节省：260MB
```

### 4.3 构建缓存（Build Cache）

解释：Docker 构建镜像时会缓存每一层。如果这一层的指令和上下文没有变化，就直接复用缓存，不重新执行。这是加速构建的关键。

**缓存命中的条件：**
- 该层的 Dockerfile 指令完全相同
- 该层用到的文件内容没有变化（针对 COPY/ADD 指令）
- 上面所有层的缓存都命中（某一层缓存失效，后面所有层都会重新执行）

**典型的错误写法（缓存利用不好）：**
```dockerfile
FROM python:3.11-slim

WORKDIR /app

# 错误：每次改任何代码，这一句 COPY 就让后面所有层缓存失效
# 包括 pip install，每次都要重新安装所有依赖
COPY . .
RUN pip install -r requirements.txt

CMD ["python", "app.py"]
```

**正确写法（充分利用缓存）：**
```dockerfile
FROM python:3.11-slim

WORKDIR /app

# 正确：先单独 COPY requirements.txt
# 只要依赖没变，pip install 这层就能命中缓存
COPY requirements.txt .
RUN pip install -r requirements.txt

# 最后才 COPY 代码，代码经常改，但只影响这一层以后的层
COPY . .

CMD ["python", "app.py"]
```

区别：
- 错误写法：每次改一行代码，都要重新 pip install 所有依赖（可能 3-5 分钟）
- 正确写法：只改代码不改依赖，pip install 命中缓存（几秒钟）

### 4.4 镜像层的写时复制（Copy-on-Write）

解释：容器对文件的修改不会影响原始镜像层，而是写到容器自己的可写层。

```
只读层（镜像层，共享）
├── 第 1 层：OS 文件
├── 第 2 层：Python 运行时
└── 第 3 层：你的应用代码

可写层（容器层，每个容器独有）
└── 容器 A 对文件的修改
└── 容器 B 对文件的修改（互相独立）
```

当容器修改一个文件时：
1. 从只读层把原文件复制到可写层（Copy-up 操作）
2. 在可写层修改这个文件副本
3. 原来只读层的文件保持不变

注意事项：如果容器内有大量的文件修改操作（比如数据库），Copy-on-Write 会有性能开销。这也是为什么数据库数据要用 Volume，而不能直接写在容器层里。

### 4.5 悬空镜像（Dangling Images）

解释：重新构建同名镜像后，旧镜像被新镜像"顶替"了名字，旧镜像就变成了没有名字和标签的"悬空镜像"（dangling image），占磁盘空间但没什么用。

```bash
# 查看所有悬空镜像（名字显示为 <none>）
docker images -f dangling=true

# 删除所有悬空镜像
docker image prune
```

## 8. 常见误区

1. 误区：层越多，镜像越大。  
   解释：不一定。空指令（ENV/EXPOSE/CMD）不增加大小。真正增大镜像的是 RUN/COPY/ADD 里引入的文件。可以用 `docker history` 看每层的大小。

2. 误区：RUN 指令里删除的文件能减小镜像大小。  
   解释：不行！删除操作在新的层里，旧层的文件还在。要减小镜像，必须在同一个 RUN 指令里安装并清理，比如 `RUN apt-get install && apt-get clean && rm -rf /var/lib/apt/lists/*`。

## 9. 本节总结

Docker 镜像是分层叠加的只读文件系统，每层对应 Dockerfile 的一条指令。分层设计让镜像可以共享底层，节省磁盘。构建缓存按层缓存，某层失效后面全部失效——所以要把"经常变的东西"放后面，"不常变的依赖安装"放前面。容器对文件的修改写在可写层，不影响镜像。
