# 14 检索策略与上下文编排

GraphRAG 的查询不是简单 `top_k=5`。  
真正的难点是：用户问题来了以后，到底走哪条检索路线？召回的内容怎么组织给大模型？

---

## 本节学习目标

学完本节后，你应该能：

- 区分 query intent、local search、global search、hybrid search。
- 理解多路召回和重排。
- 知道上下文预算是什么。
- 能设计一个可解释的 GraphRAG 检索编排流程。
- 知道为什么上下文不是越多越好。

---

## 核心概念解释

### 1. Query Intent

Query Intent 是用户问题的意图。

例如：

```text
事实查询：付款期限是多少？
关系查询：项目 A 和合同 B 有什么关系？
全局总结：这批合同有哪些风险？
路径查询：登录接口调用链路是什么？
对比查询：A 方案和 B 方案有什么区别？
```

不同意图适合不同检索策略。

### 2. 多路召回

多路召回是从多个入口找候选内容：

```text
向量 chunk 召回
实体名匹配
实体 embedding 召回
图邻居扩展
社区摘要召回
关键词召回
```

### 3. 重排

重排是对候选内容重新排序。

原因是：

```text
最先召回的不一定最适合放进 prompt。
```

### 4. 上下文预算

大模型上下文长度有限。  
上下文预算就是决定：

```text
最多放多少 chunk？
最多放多少关系？
最多放多少社区摘要？
每种内容占多少 token？
```

### 5. Context Builder

Context Builder 是专门负责组装上下文的模块。

它决定：

```text
先放问题相关实体？
再放关系？
再放原文？
还是先放社区摘要？
```

## 通俗理解

检索像做菜备料。

多路召回是去不同地方拿食材：

```text
向量库拿文本片段。
图数据库拿实体关系。
社区摘要库拿主题总结。
关键词搜索拿精确术语。
```

上下文编排是决定怎么装盘：

```text
哪些食材留下？
哪些丢掉？
先放主菜还是配菜？
模型最需要看到什么？
```

如果什么都往 prompt 里塞，模型可能反而答不好。

## 技术流程图

```text
用户问题
-> query intent 判断
-> 多路召回
   -> vector chunks
   -> matched entities
   -> graph neighbors
   -> community reports
   -> keywords
-> 合并候选
-> 去重
-> 重排
-> 上下文预算分配
-> context builder 组装 prompt
-> LLM 生成答案
-> 返回答案、引用、检索路径
```

上下文预算示例：

```text
总预算：6000 tokens
社区摘要：1500
实体关系：1500
原文 chunk：2500
系统指令和问题：500
```

## 关键代码/伪代码示例

### 1. 意图判断

```python
def classify_query_intent(question: str) -> str:
    if any(word in question for word in ["整体", "主要", "总结", "有哪些风险"]):
        return "global"
    if any(word in question for word in ["关系", "关联", "影响", "调用链"]):
        return "local"
    return "hybrid"
```

### 2. 多路召回

```python
def retrieve_candidates(question: str, intent: str) -> dict:
    candidates = {}

    candidates["vector_chunks"] = vector_search_chunks(question)

    entities = match_entities(question)
    candidates["entities"] = entities

    if intent in ["local", "hybrid"]:
        candidates["graph_relations"] = expand_graph_neighbors(entities)

    if intent in ["global", "hybrid"]:
        candidates["community_reports"] = search_community_reports(question)

    return candidates
```

### 3. 上下文构建

```python
def build_context(candidates: dict, budget: dict) -> str:
    parts = []

    reports = select_top(candidates.get("community_reports", []), budget["reports"])
    relations = select_top(candidates.get("graph_relations", []), budget["relations"])
    chunks = select_top(candidates.get("vector_chunks", []), budget["chunks"])

    parts.append(format_reports(reports))
    parts.append(format_relations(relations))
    parts.append(format_chunks(chunks))

    return "\n\n".join(parts)
```

### 4. 返回检索路径

```python
return {
    "answer": answer,
    "sources": source_chunks,
    "retrieval": {
        "mode": intent,
        "entities": [entity.name for entity in entities],
        "relation_count": len(relations),
        "report_count": len(reports),
        "chunk_count": len(chunks),
    },
}
```

## 实际项目中怎么用

### `/ask` 请求体

```json
{
  "question": "这批合同有哪些主要风险？",
  "mode": "auto",
  "top_k": 8,
  "include_sources": true
}
```

### `/ask` 响应体

```json
{
  "answer": "...",
  "mode": "global",
  "sources": [],
  "retrieval": {
    "report_count": 5,
    "chunk_count": 6,
    "entity_count": 12
  }
}
```

### 场景建议

企业知识库：

```text
制度解释：vector + local
制度总览：global
流程关联：local
```

合同审查：

```text
单份合同条款：vector
某个主体风险：local
整批合同风险：global + hybrid
```

代码知识库：

```text
函数解释：vector
调用链路：local
架构总结：global
```

## 容易混淆的点

### 1. auto mode 不要一开始做太复杂

可以先用规则判断。  
后面再用 LLM 做 query intent 分类。

### 2. 上下文不是越多越好

太多上下文会引入噪声，也会增加成本。

### 3. 图关系不能替代原文证据

图关系适合导航，原文 chunk 适合证明。

### 4. 重排不是必须第一版就做

新手第一版可以先合并去重。  
第二版再加 reranker。

### 5. 检索结果要可解释

返回 `retrieval` 信息有助于调试：

```text
系统用了哪些实体？
召回了哪些社区？
用了多少 chunk？
```
