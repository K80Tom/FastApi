# 13 社区发现与社区摘要深化

GraphRAG 之所以能回答全局问题，很大程度依赖社区发现和社区摘要。  
这一节专门把这两个概念讲深一点。

---

## 本节学习目标

学完本节后，你应该能：

- 理解社区发现为什么重要。
- 知道社区不是人工分类。
- 理解社区摘要如何支撑全局检索。
- 知道社区划分太粗或太细会有什么问题。
- 能设计一个简单的社区摘要生成流程。

---

## 核心概念解释

### 1. 社区

社区是图中联系紧密的一组节点。

例如：

```text
财务部、报销流程、发票、审批人、报销上限
```

这些节点互相关联较多，就可能形成“报销流程社区”。

### 2. 社区发现

社区发现是根据图结构自动找主题团块。

它不是看文档标题，也不是人工分类，而是看：

```text
哪些节点之间连接更密？
哪些节点更常共同出现？
哪些关系把它们组成一个相对独立的区域？
```

### 3. 层级社区

有些图可以形成层级：

```text
公司制度
  -> 财务制度
    -> 报销流程
    -> 预算审批
  -> 人事制度
    -> 入职流程
    -> 转正流程
```

GraphRAG 中，全局总结可能需要不同粒度的社区报告。

### 4. 社区摘要

社区摘要是对一个社区的结构化总结。

它应该包含：

```text
社区主题
关键实体
关键关系
主要事实
潜在风险
来源证据
```

### 5. Global Search

Global Search 通常依赖社区摘要，而不是直接检索所有原文 chunk。  
它适合回答全局主题类问题。

---

## 通俗理解

你可以把社区发现理解成整理一张复杂关系网：

```text
图上有几千个点。
你先不看每个点，而是看哪些点抱成一团。
每一团就是一个主题区域。
然后给每个主题区域写一份摘要。
```

用户问：

```text
“这批合同主要有哪些风险？”
```

系统不需要把所有合同 chunk 都塞给模型。  
它可以先看每个风险相关社区的摘要，再汇总回答。

## 技术流程图

```text
实体关系图
-> 社区发现算法
-> 得到多个 community
-> 收集每个 community 的实体、关系、来源 chunk
-> LLM 生成 community report
-> 为 community report 生成 embedding
-> 查询时检索 report
-> LLM 基于 report 回答全局问题
```

社区报告结构：

```text
community_id
title
summary
key_entities
key_relations
source_chunk_ids
level
rank
embedding
```

def build_community_summary_input(community):
    entities = entity_repo.find_by_ids(community.entity_ids)
    relations = relation_repo.find_inside_community(community.entity_ids)
    chunks = chunk_repo.find_by_ids(collect_source_chunk_ids(relations))

### 3. 社区摘要 prompt

```text
请根据下面的实体、关系和原文证据，总结这个社区。

要求：
1. 给出社区标题。
2. 总结这个社区的主题。
3. 列出关键实体。
4. 列出关键关系。
5. 如果存在风险或冲突，请指出。
6. 不要编造没有证据的信息。

实体：
{entities}

关系：
{relations}

证据：
{chunks}
```

## 容易混淆的点

### 1. 社区不是文档分类

一个文档里的实体可能分布到多个社区。  
一个社区也可能跨多个文档。

### 2. 社区太粗会丢细节

如果一个社区包含太多实体，摘要会变空泛。

### 3. 社区太细会失去全局价值

如果社区太碎，全局检索时又会变成很多小片段。

### 4. 社区摘要会继承抽取错误

如果实体关系抽错，社区摘要也可能错。

### 5. 社区摘要不是最终事实源

重要答案最好还能回到原文 chunk 验证。
