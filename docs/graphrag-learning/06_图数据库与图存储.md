# 06 图数据库与图存储

前面已经知道 GraphRAG 会抽取实体和关系。本节解决一个工程问题：这些图数据应该怎么存？

---

## 本节学习目标

学完本节后，你应该能：

- 理解图数据库是什么。
- 知道节点、边、属性在数据库中怎么表示。
- 区分图数据库、关系型数据库、向量数据库的职责。
- 设计一个新手可实现的 GraphRAG 存储方案。
- 知道什么时候需要 Neo4j，什么时候可以先用 PostgreSQL。

---

## 核心概念解释

### 1. 图数据库

图数据库是专门存储和查询图结构的数据库。

它擅长回答：

```text
某个节点连接了哪些节点？
两个节点之间有什么路径？
哪些节点在同一个社区？
某个实体的二跳邻居有哪些？
```

常见图数据库：

```text
Neo4j
NebulaGraph
Amazon Neptune
ArangoDB
```

### 2. 节点

节点通常表示实体。

例如：

```text
张三
项目 A
FastAPI
合同 B
```

### 3. 边

边通常表示关系。

例如：

```text
张三 --负责--> 项目 A
项目 A --使用--> FastAPI
```

### 4. 属性

节点和边都可以有属性。

节点属性：

```text
name
type
description
source_document_id
```

边属性：

```text
type
description
confidence
source_chunk_id
```

### 5. 向量数据库

向量数据库负责语义相似度检索。

它和图数据库不是同一个角色：

```text
图数据库：保存关系。
向量数据库：保存语义向量。
```

GraphRAG 项目里经常两个都需要。

---

## 通俗理解

如果把知识库看成城市：

```text
关系型数据库像 Excel 表，适合保存整齐记录。
向量数据库像语义搜索引擎，适合找意思相近的文本。
图数据库像地图，适合找对象之间的连接路径。
```

GraphRAG 要用图，是因为它不仅关心：

```text
哪段文字最像问题？
```

还关心：

```text
这个实体和谁有关？
它们之间是什么关系？
它属于哪个主题社区？
相关原文证据在哪里？
```

---

## 技术流程图

一种常见存储结构：

```text
documents 表
  -> 保存原始文档元数据

chunks 表
  -> 保存切块文本和来源

entities 表
  -> 保存实体节点

relations 表
  -> 保存实体之间的边

communities 表
  -> 保存社区信息

community_reports 表
  -> 保存社区摘要

vector store
  -> 保存 chunk/entity/report 的 embedding
```

如果使用图数据库：

```text
PostgreSQL：documents、chunks、任务状态、用户
Neo4j：entities、relations、graph query
Vector DB：embedding 检索
```

如果新手先简化：

```text
PostgreSQL 或 SQLite：
documents
chunks
entities
relations
communities
community_reports

Chroma 或 pgvector：
embeddings
```

## 关键代码/伪代码示例

### 1. 用表保存图

新手可以先不用图数据库，用两张表保存节点和边。

```python
entities = [
    {
        "id": "ent_001",
        "name": "FastAPI",
        "type": "Technology",
        "description": "一个 Python Web API 框架",
    }
]

relations = [
    {
        "id": "rel_001",
        "source_entity_id": "ent_project_a",
        "target_entity_id": "ent_fastapi",
        "type": "使用",
        "description": "项目 A 使用 FastAPI 开发接口",
        "source_chunk_id": "chunk_001",
    }
]
```

查询某个实体的邻居：

```python
def get_neighbors(entity_id: str) -> list[dict]:
    outgoing = relation_repo.find_by_source(entity_id)
    incoming = relation_repo.find_by_target(entity_id)
    return outgoing + incoming
```

### 2. 图数据库查询伪代码

如果用 Neo4j，查询邻居通常类似：

```cypher
MATCH (e:Entity {name: "FastAPI"})-[r]-(neighbor)
RETURN e, r, neighbor
LIMIT 20
```

意思是：

```text
找到名为 FastAPI 的实体，以及和它相连的关系和邻居节点。
```

### 3. 保存来源证据

关系最好记录来自哪个 chunk：

```python
relation = {
    "source": "项目 A",
    "target": "FastAPI",
    "type": "使用",
    "source_chunk_id": "chunk_123",
}
```

这样回答时可以回到原文：

```text
这个关系不是凭空来的，它来自 chunk_123。
```

## 实际项目中怎么用

### 新手最小方案

如果你现在还在学 FastAPI 和数据库，建议先用：

```text
SQLite / PostgreSQL + Chroma
```

表结构：

```text
documents(id, title, source_path, created_at)
chunks(id, document_id, text, page, section)
entities(id, name, type, description)
relations(id, source_entity_id, target_entity_id, type, description, source_chunk_id)
community_reports(id, title, summary)
```

这样已经能做一个可展示 Demo。

### 进阶方案

如果数据规模变大，或者你需要复杂图查询，可以用：

```text
PostgreSQL + Neo4j + 向量数据库
```

分工：

```text
PostgreSQL：业务数据和任务状态
Neo4j：实体关系图
向量数据库：语义检索
```

### Agent 记忆系统

可以这样存：

```text
User -> 提出 -> Goal
Goal -> 拆解为 -> Task
Task -> 调用 -> Tool
Tool -> 产生 -> Result
Result -> 支持 -> Decision
```

这样 Agent 后续可以沿着关系找回历史。

## 容易混淆的点

### 1. 图数据库不是 GraphRAG 的全部

GraphRAG 不是“用了 Neo4j 就叫 GraphRAG”。  
重点是图参与了检索和上下文组织。

### 2. 新手不一定要一开始上图数据库

小项目可以先用关系型数据库保存节点和边。  
等理解流程后再换 Neo4j。

### 3. 向量数据库不能替代图数据库

向量数据库找语义相似。  
图数据库找关系连接。  
二者解决的问题不同。

### 4. 关系必须保存来源

如果关系没有来源 chunk，回答时很难解释证据来自哪里。

### 5. 图数据也需要去重

同一实体、同一关系可能从多个 chunk 抽出来。  
要考虑合并和去重。
