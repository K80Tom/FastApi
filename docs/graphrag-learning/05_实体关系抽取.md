# 05 实体关系抽取

前一节讲了 GraphRAG 的数据处理流程。本节聚焦其中最关键的一步：如何从文本里抽取实体和关系。

---

## 本节学习目标

学完本节后，你应该能：

- 理解实体抽取和关系抽取分别做什么。
- 知道为什么 GraphRAG 很依赖抽取质量。
- 能写一个简单 prompt 抽取实体和关系。
- 知道抽取结果为什么需要清洗、合并和校验。
- 能把抽取结果设计成结构化 JSON。

---

## 核心概念解释

### 1. 实体抽取

实体抽取就是从文本中找出重要对象。

例如文本：

```text
张三负责智能客服项目，该项目使用 FastAPI 和 PostgreSQL。
```

实体可以是：

```text
张三：Person
智能客服项目：Project
FastAPI：Technology
PostgreSQL：Technology
```

### 2. 关系抽取

关系抽取就是找出实体之间的联系。

例如：

```text
张三 -> 负责 -> 智能客服项目
智能客服项目 -> 使用 -> FastAPI
智能客服项目 -> 使用 -> PostgreSQL
```

### 3. 实体类型

实体类型是实体的分类。

例如：

```text
Person
Organization
Project
Contract
Technology
Module
Function
Risk
```

实体类型不用一开始设计得特别复杂。  
新手项目可以先从 5 到 8 个常见类型开始。

### 4. 关系类型

关系类型是关系的分类。

例如：

```text
负责
属于
使用
依赖
调用
包含
影响
导致
约束
```

关系类型最好尽量稳定，否则图会很乱。

### 5. 结构化输出

结构化输出就是让 LLM 不要随便写自然语言，而是按固定 JSON 格式输出。

例如：

```json
{
  "entities": [],
  "relations": []
}
```

这样程序才能继续处理。

---

## 通俗理解

实体关系抽取像读文章时做标注：

```text
先用荧光笔圈出重要名词。
再用箭头标出它们之间的关系。
最后把这些圈和箭头整理成表格。
```

GraphRAG 的图质量，很大程度取决于这一步。  
如果实体抽漏了，后面图上就没有这个点。  
如果关系抽错了，后面检索就会沿着错误的边走。

---

## 技术流程图

```text
chunk 文本
-> prompt 模板
-> LLM 抽取
-> JSON 解析
-> 字段校验
-> 实体标准化
-> 关系校验
-> 保存 entities 和 relations
```

更细一点：

```text
输入 chunk:
“项目 A 使用 FastAPI，张三负责项目 A。”

抽取实体:
项目 A、FastAPI、张三

抽取关系:
项目 A -> 使用 -> FastAPI
张三 -> 负责 -> 项目 A

校验:
关系里的 source 和 target 必须能在实体列表里找到

入库:
entities 表、relations 表
```

## 关键代码/伪代码示例

### 1. Prompt 示例

```text
请从下面文本中抽取实体和关系。

要求：
1. 实体类型只能是 Person、Organization、Project、Technology、Contract、Risk、Concept。
2. 关系要表达两个实体之间的明确联系。
3. 输出必须是 JSON，不要输出额外解释。

输出格式：
{
  "entities": [
    {"name": "...", "type": "...", "description": "..."}
  ],
  "relations": [
    {"source": "...", "target": "...", "type": "...", "description": "..."}
  ]
}

文本：
{chunk_text}
```

### 2. 抽取函数伪代码

```python
def extract_entities_and_relations(chunk_text: str) -> dict:
    prompt = build_extraction_prompt(chunk_text)
    raw_output = llm.generate(prompt)
    data = parse_json(raw_output)
    validate_extraction_result(data)
    return data
```

### 3. 校验逻辑伪代码

```python
def validate_extraction_result(data: dict) -> None:
    entity_names = {entity["name"] for entity in data["entities"]}

    for relation in data["relations"]:
        if relation["source"] not in entity_names:
            raise ValueError("relation source not found in entities")
        if relation["target"] not in entity_names:
            raise ValueError("relation target not found in entities")
```

### 4. 实体标准化伪代码

```python
def normalize_entity_name(name: str) -> str:
    return name.strip().lower()


def merge_entities(entities: list[dict]) -> list[dict]:
    merged = {}
    for entity in entities:
        key = normalize_entity_name(entity["name"])
        if key not in merged:
            merged[key] = entity
        else:
            merged[key]["description"] += "\n" + entity.get("description", "")
    return list(merged.values())
```

## 容易混淆的点

### 1. 不要让实体类型太多

实体类型太多，新手会很难维护。  
先少而清晰，再逐步扩展。

### 2. 不要把所有词都抽成实体

实体应该服务于问答和检索。  
如果一个词对后续检索没有价值，可以不抽。

### 3. 不要完全相信 LLM 输出

LLM 可能输出不合法 JSON，也可能关系里引用了不存在的实体。  
所以要做解析和校验。

### 4. 抽取结果不是最终答案

抽取结果是索引材料。  
最终回答仍然要结合原文证据和 LLM 生成。

### 5. 实体合并很重要

如果不合并：

```text
FastAPI
fastapi
FastAPI 框架
```

可能会变成三个节点，导致图被拆散。
