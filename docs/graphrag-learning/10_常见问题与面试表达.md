## 核心概念解释

### 1. GraphRAG 一句话表达

可以这样说：

```text
GraphRAG 是在普通 RAG 的基础上，把文档中的实体和关系构造成知识图谱，再利用图结构和社区摘要增强检索与问答的方法。
```

更口语一点：

```text
普通 RAG 主要找相似文本，GraphRAG 还会看知识之间的关系。
```

### 2. 实体

实体是知识中的重要对象。

例如：

```text
人、公司、项目、合同、模块、函数、条款、风险
```

### 3. 关系

关系是实体之间的连接。

例如：

```text
负责、属于、调用、依赖、包含、导致、影响
```

### 4. 社区发现

社区发现是从图里找出联系紧密的一组实体。

例如：

```text
合同审批相关实体形成一个社区。
报销流程相关实体形成一个社区。
登录模块相关函数形成一个社区。
```

### 5. 全局检索

全局检索适合宏观总结：

```text
“这批文档主要讲什么？”
“有哪些主要风险？”
“系统核心模块有哪些？”
```

### 6. 局部检索

局部检索适合围绕具体实体查关系：

```text
“项目 A 关联哪些合同？”
“UserService 调用了哪些函数？”
“供应商 B 有哪些风险条款？”
```

### 7. 混合检索

混合检索是把图检索和向量检索结合起来：

```text
向量找语义相似内容。
图找实体关系路径。
二者合并后给 LLM。
```

## 通俗理解

如果面试官问：

```text
“GraphRAG 到底比 RAG 多了什么？”
```

你可以这样说：

```text
普通 RAG 像是在文档里找几段和问题相似的话。
GraphRAG 会先把文档里的关键对象和它们之间的关系整理成一张知识地图。
提问时，系统不仅能找相似文本，还能沿着知识地图找相关实体、关系和主题社区。
所以它更适合跨文档、多实体、全局总结和关系推理类问题。
```

这段话比只说“GraphRAG 用了知识图谱”更清楚。

## 技术流程图

面试时可以画这个简化图：

```text
离线索引：
文档
-> chunk
-> LLM 抽取实体和关系
-> 构建知识图谱
-> 社区发现
-> 社区摘要
-> 保存图数据和向量

在线问答：
用户问题
-> 判断全局 / 局部 / 混合检索
-> 检索社区摘要、实体邻居、原文 chunk
-> 组装上下文
-> LLM 生成答案
-> 返回答案和引用来源
```

## 关键代码/伪代码示例

面试或项目介绍中，不一定要写完整代码，可以写核心伪代码：

```python
def build_index(documents):
    chunks = split_documents(documents)
    entities, relations = extract_entities_and_relations(chunks)
    graph = build_graph(entities, relations)
    communities = detect_communities(graph)
    reports = summarize_communities(communities)
    save_index(chunks, graph, reports)


def ask(question):
    if is_global_question(question):
        context = global_search(question)
    elif has_specific_entity(question):
        context = local_search(question)
    else:
        context = hybrid_search(question)

    return llm_answer(question, context)
```

重点解释：

```text
build_index 是离线阶段。
ask 是在线阶段。
GraphRAG 的核心在于 graph、communities、reports 参与检索。
```

## 实际项目中怎么用

### 项目介绍模板

你可以这样介绍自己的项目：

```text
我做了一个基于 GraphRAG 的企业知识库问答系统。
系统先把上传文档切分成 chunk，再用 LLM 抽取实体和关系，构建知识图谱。
然后对图做社区发现，并为每个社区生成摘要。
用户提问时，系统会根据问题类型选择局部检索、全局检索或混合检索。
局部检索会围绕具体实体扩展邻居关系，全局检索会使用社区摘要回答宏观问题。
最后系统把检索到的图关系、社区摘要和原文 chunk 交给 LLM 生成答案，并返回引用来源。
```

### 项目亮点表达

可以强调：

```text
1. 不只做向量相似检索，还显式建模实体关系。
2. 支持全局问题和局部问题两类检索。
3. 回答可以追溯到原文 chunk。
4. 架构上按文档处理、抽取、图存储、检索、生成分层。
```

## 容易混淆的点

### 1. GraphRAG 和知识图谱不是一回事

知识图谱是知识组织方式。  
GraphRAG 是把知识图谱用于 RAG 检索和问答。

### 2. GraphRAG 和向量 RAG 不是敌人

GraphRAG 经常和向量检索结合。  
图负责关系，向量负责语义相似。

### 3. 全局检索不是全库暴力搜索

全局检索依赖社区摘要等压缩后的全局信息。  
不是把所有文档都丢给模型。

### 4. 社区发现不是人工分类

社区发现是根据图结构自动找联系紧密的节点群。  
人工分类通常是人为给文档打标签。

### 5. GraphRAG 也有成本

它需要额外的抽取、清洗、合并、图构建和摘要生成。  
如果数据量小、问题简单，普通 RAG 可能更合适。

## 常见面试问题参考回答

### 1. GraphRAG 解决了什么问题？

回答：

```text
它主要解决普通 RAG 对跨文档关系、全局总结和多实体关联问题支持不好的问题。
普通 RAG 依赖 chunk 相似度，容易只召回局部文本。
GraphRAG 把文档中的实体和关系构成图，查询时可以沿着图扩展相关信息，也可以用社区摘要回答全局问题。
```

### 2. 为什么需要社区发现？

回答：

```text
社区发现可以把图中联系紧密的实体聚成主题区域。
这样系统能为每个主题区域生成摘要。
当用户问全局问题时，不需要遍历所有 chunk，而是可以检索这些社区摘要作为高层上下文。
```

### 3. GraphRAG 的缺点是什么？

回答：

```text
GraphRAG 的构建成本比普通 RAG 高，需要实体关系抽取、去重、图构建和社区摘要。
抽取质量会影响最终效果。
另外，如果业务问题只是简单事实问答，普通向量 RAG 可能更简单、更便宜。
```

### 4. 怎么评价 GraphRAG 效果？

回答：

```text
可以从召回质量、答案准确性、引用来源正确性、全局总结质量、关系推理质量几个方面评估。
项目中还可以准备一组标准问题，对比普通 RAG 和 GraphRAG 在跨文档问题上的表现。
```
