# 13 模型部署与调用

## 1. 这一节要解决什么问题

这一节帮你理解微调后模型如何推理、如何加载 LoRA、是否需要合并 LoRA，以及如何用 API、Ollama、vLLM 等方式对外提供服务。

## 2. 基础概念解释

### Inference 推理

通俗解释：推理就是训练结束后，让模型正式回答用户问题。

技术解释：Inference 是固定模型权重后，根据输入 token 逐步生成输出 token 的过程。

例子：用户问“什么是 QLoRA”，模型生成解释。

### Merge LoRA

通俗解释：Merge LoRA 像把便签内容抄进教材，让部署时只带一本合并后的书。

技术解释：Merge LoRA 是把 LoRA adapter 权重合并到基础模型权重中，生成独立模型权重。

例子：`base model + adapter` 可以动态加载，merge 后可以像普通模型一样加载。

### vLLM

通俗解释：vLLM 像一个高效餐厅后厨，专门让模型更快、更稳定地接待很多请求。

技术解释：vLLM 是高性能大模型推理服务框架，常用于 OpenAI API 兼容服务和高吞吐推理。

例子：部署一个模型服务，应用通过 HTTP API 调用它。

### Ollama

通俗解释：Ollama 像本地模型管理器，可以方便地下载、运行和调用模型。

技术解释：Ollama 是本地运行大模型的工具，适合个人电脑上管理和调用量化模型。

例子：用 Ollama 在本地启动一个聊天模型，再用 API 请求它。

### API 部署

通俗解释：API 部署像给模型开一个窗口，别的程序通过固定地址来问它问题。

技术解释：API 部署是把模型推理封装为 HTTP 接口，例如 `POST /chat`，供前端或其他后端调用。

例子：FastAPI 接收用户问题，调用模型生成答案，返回 JSON。

## 3. 为什么要学这个

微调模型只有能被调用，才算进入应用。部署阶段会遇到显存、推理速度、加载方式、并发、模型文件大小、LoRA 合并等问题。简历项目也需要展示“训练后如何服务化”。

## 4. 关键知识点

### 4.1 推理加载方式

解释：LoRA 模型常见两种推理方式。

例子：

| 方式 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 基础模型 + LoRA adapter | 推理时动态加载 adapter | 灵活，可切换多个 LoRA | 需要同时管理两部分 |
| Merge 后模型 | 把 LoRA 合并进基础模型 | 部署简单 | 占用更大，不易切换 |

注意事项：如果要维护多个领域助手，动态加载 adapter 更灵活。如果只部署一个固定模型，merge 更简单。

### 4.2 最小推理代码

解释：下面展示加载基础模型和 LoRA adapter 的思路。

例子：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel

base_model = "Qwen/Qwen2.5-0.5B-Instruct"
lora_path = "./outputs/lora-demo/final"

tokenizer = AutoTokenizer.from_pretrained(base_model, trust_remote_code=True)
model = AutoModelForCausalLM.from_pretrained(base_model, device_map="auto", trust_remote_code=True)
model = PeftModel.from_pretrained(model, lora_path)

prompt = "用户：请解释什么是 LoRA。\n助手："
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
outputs = model.generate(**inputs, max_new_tokens=128)
print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

注意事项：训练时和推理时的 prompt 模板要尽量一致，否则模型可能表现不稳定。

### 4.3 Merge LoRA 代码思路

解释：合并后保存成新模型目录。

例子：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel

base_model = "Qwen/Qwen2.5-0.5B-Instruct"
lora_path = "./outputs/lora-demo/final"
merged_path = "./outputs/lora-demo/merged"

tokenizer = AutoTokenizer.from_pretrained(base_model, trust_remote_code=True)
model = AutoModelForCausalLM.from_pretrained(base_model, device_map="auto", trust_remote_code=True)
model = PeftModel.from_pretrained(model, lora_path)
model = model.merge_and_unload()

model.save_pretrained(merged_path)
tokenizer.save_pretrained(merged_path)
```

注意事项：merge 后再量化、部署要注意格式兼容。先确认本地能正常推理。

### 4.4 FastAPI API 封装

解释：可以用 FastAPI 把推理包装成接口。

例子：

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ChatRequest(BaseModel):
    question: str

@app.post("/chat")
def chat(req: ChatRequest):
    # 真实项目中这里调用 tokenizer、model.generate
    answer = f"收到问题：{req.question}"
    return {"answer": answer}
```

注意事项：真实部署不要每次请求都重新加载模型。模型应在服务启动时加载一次。

### 4.5 vLLM 部署思路

解释：vLLM 适合需要更高吞吐和 API 服务的场景。

例子：

```text
模型目录 -> vLLM server -> OpenAI 兼容 API -> 应用调用
```

注意事项：vLLM 对模型架构、量化格式和 LoRA 支持有版本差异。做项目时先选 vLLM 支持良好的模型。

### 4.6 Ollama 部署思路

解释：Ollama 更适合本地个人体验和简单 Demo。

例子：

```text
量化模型文件 -> Ollama 管理 -> 本地 API 调用 -> 小应用
```

注意事项：HuggingFace/PEFT 的 LoRA adapter 不能总是直接丢给 Ollama，需要转换或合并到支持格式。

### 4.7 生成参数

解释：推理时生成参数会影响输出风格。

例子：

| 参数 | 通俗理解 | 影响 |
| --- | --- | --- |
| max_new_tokens | 最多回答多少字 | 防止太长或被截断 |
| temperature | 随机程度 | 越高越发散 |
| top_p | 候选词范围 | 控制多样性 |
| repetition_penalty | 防重复 | 减少重复句子 |

注意事项：评估时生成参数要固定，否则结果不公平。

## 8. 常见误区

1. 误区：保存 LoRA 后就能直接当完整模型部署。  
   解释：LoRA adapter 通常需要基础模型一起加载。

2. 误区：部署只需要能回答一次。  
   解释：真实服务还要考虑响应时间、并发、显存和异常处理。

3. 误区：temperature 越高越聪明。  
   解释：temperature 高会更随机，事实类问答通常不宜太高。

4. 误区：训练 prompt 和推理 prompt 可以完全不同。  
   解释：模板差异过大可能导致模型不按训练习惯回答。

## 9. 本节总结

微调后的模型需要经过推理加载、可能的 LoRA 合并、API 封装和部署选择，才能真正服务应用。FastAPI 适合教学和项目闭环，Ollama 适合本地体验，vLLM 适合更高性能服务。部署前要先确认模型在本地推理稳定。
